Persist who the server is, resolve where it is

Issue #133 was filed as an Android permission bug. It wasn’t — the grant was present the whole time. The real fault was #131: the desktop advertised a Parallels host-only address, and the client stored that unroutable URL as the permanent identity of the connection.

What actually changed

An IP address is a DHCP lease, not an identity. Storing one as the connection’s primary key meant any address change bricked the client with no recovery path — discovery couldn’t help, because the client stops browsing the moment a config row exists.

How resolution works

The cached address is tried first because it is almost always right. Identity is what makes the failure case recoverable, and what stops the client uploading to a stranger’s machine after a DHCP reshuffle.

Delivered in three dependent phases

01

A connection state that can express uncertainty

ServerConnectionState replaces a bare boolean with Unknown, Checking, Resolving, Connected, Unreachable and IdentityMismatch. A boolean shim keeps every existing caller’s semantics unchanged. Side effect: an unconfigured client no longer shows a red status dot for a problem it doesn’t have.

02

The server publishes an identity

A UUID minted once and preserved across reconfiguration, served from GET /health and advertised in structured mDNS TXT records (id, v, name, scheme, addrs). Keys and codec live in shared code so the two ends can’t drift. A newer client falls back to the old liveness route on a 404, so a phone updated ahead of its desktop still connects.

03

The client resolves by identity

Config now carries identity only, so re-resolving no longer restarts the health poll or blanks the photo feed. Both discovery implementations read TXT records; iOS additionally gained IPv4 preference and IPv6 bracketing, which it never had.

Two defects found while reviewing my own work

  • Identity could be minted twice. getOrCreateServerId() generated a UUID but never persisted it, so the name lied and any caller before configuration would get a different id each time. Minting now happens in exactly one place.
  • Manual pairings could never recover. A typed-in address stores no identity, and the resolver bailed straight to Unreachable — making the most common pairing path the one that could never self-heal. The client now adopts the identity the server reports on first successful probe, guarded in SQL so it can never repoint an already-identified client.

Sync is untouched

An earlier attempt to bound three unbounded waits broke sync on Android and was fully reverted. The wait in LocalMediaManager turned out to be load-bearing: it is how a client launched before it has a server starts syncing once one is connected. Bounding it meant connecting afterwards did nothing.

Those files are now byte-identical to HEAD apart from one two-line delegating override that the interface change requires. The concerns are recorded in #139, including that constraint, so the same wrong fix isn’t attempted again.
